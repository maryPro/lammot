# Процесс исправления багов

Цель: каждый баг чинится отдельно, проверяется тестами и ручным сценарием
и только потом попадает в `main`. `main` всегда рабочая и задеплоенная
версия. Merge в `main` — это деплой на Railway, поэтому «потом поправим»
не работает.

## Принципы

1. **Один баг = один Issue = одна ветка = один чат с ИИ = один PR.**
   Новый баг — новый чат с чистым контекстом.
2. **Ветка всегда от свежего `main`.** Не чини баг в старой ветке, которая
   отстала на много коммитов.
3. **Маленький дифф.** Обычно 1–3 файла. Если ИИ трогает больше или выходит
   за разрешённый список — остановись и разберись.
4. **Сначала красный тест, потом фикс.** Тест должен падать до исправления
   и проходить после. Иначе нет доказательства, что баг починен.
5. **Merge только после:** зелёный CI, регрессионный тест, ручная проверка,
   просмотр диффа.
6. **Тестовый бот отдельно от прод-бота.** У токена один вебхук: локальный
   сервер с прод-токеном перехватит бота у Railway.

## Именование веток

- `fix/<номер-issue>-<короткий-slug>` — исправление бага,
  например `fix/12-radio-duplicate`.
- `chore/<slug>` — обслуживание: CI, зависимости, документация.
- `feat/<slug>` — новая функциональность.

## Цикл

### 1. Триаж и Issue

Проверь, что баг воспроизводится. Создай Issue по шаблону
`.github/ISSUE_TEMPLATE/bug.md`: что происходит, как воспроизвести,
ожидаемо/фактически, критичность, предполагаемые файлы, критерии приёмки.

Чем точнее описан баг, тем меньше ИИ додумывает и тем меньше дифф.

### 2. Ветка и worktree

Для каждого бага — отдельный worktree в Agent Manager (base branch `main`)
или отдельная папка. Так параллельные чаты не мешают друг другу.

Вручную:

```bash
git checkout main
git pull
git checkout -b fix/12-radio-duplicate
```

### 3. Задание для ИИ

Первым сообщением передай полный контракт, а не «почини баг».
Шаблон:

```text
Ты работаешь в отдельной ветке fix/12-radio-duplicate и отдельном worktree.
main трогать запрещено. Не переключай ветки и не делай merge.

Проект: Telegram Mini App «Lammot» — FastAPI + SQLite + HTML/JS.
Архитектура: ARCHITECTURE.md. Правила проекта: AGENTS.md.

БАГ #12: в радио-очереди повторяется тот же исполнитель подряд.
Воспроизведение: поиск → трек → очередь Up next → следующий трек того же артиста.
Ожидаемо: не более 1 трека артиста на 4 трека (app/radio.py).
Фактически: артист повторяется два раза подряд.

РАЗРЕШЁННЫЕ ФАЙЛЫ: app/radio.py, tests/test_radio.py.
ЗАПРЕЩЕНО: рефакторинг, переименования, форматирование чужих файлов,
изменения app/main.py, app/database.py, frontend/, зависимостей и схемы БД.

ОБЯЗАТЕЛЬНО:
1) Сначала добавь регрессионный тест, который падает на текущем коде.
2) Сделай минимальный фикс только в разрешённых файлах.
3) Прогони: /Users/mariia/lammot-main/venv/bin/python -m pytest -m "not integration" -v
4) В конце отчитайся: список изменённых файлов, `git diff --stat main...HEAD`,
   результат тестов, что осталось не сделано и почему.
5) Если для фикса нужно тронуть больше 3 файлов или другой слой — остановись
   и спроси разрешение, ничего не меняя.
```

### 4. Red → green

1. ИИ добавляет тест, воспроизводящий баг. Тест падает.
2. ИИ делает минимальный фикс.
3. Тест проходит, полный набор тестов зелёный.

Если ИИ не показал падающий тест — попроси показать вывод до фикса.

### 5. Проверка диффа

```bash
git diff --stat main...HEAD
git diff main...HEAD
```

Стоп-сигналы:

- файлы вне разрешённого списка;
- массовое переформатирование;
- переименования и «заодно улучшил»;
- изменения зависимостей, схемы БД или публичных API без разрешения;
- тест не воспроизводит баг.

### 6. Полный прогон тестов

```bash
/Users/mariia/lammot-main/venv/bin/python -m pytest -m "not integration" -v
```

Интеграционные тесты (`-m integration`) ходят в реальный YouTube: запускай
их только осознанно.

### 7. Ручная проверка

Запусти сервер на **тестовом** боте:

```bash
cp .env /tmp/lammot-env-backup   # если планируешь менять
cloudflared tunnel --url http://localhost:8000   # или ngrok http 8000
# новый URL → PUBLIC_URL в .env
source venv/bin/activate
uvicorn app.main:app --env-file .env --port 8000 --reload
```

Проверь сценарий бага и 2–3 соседних сценария: поиск, воспроизведение,
избранное/плейлисты. `cloudflared` quick tunnel меняет URL при каждом
перезапуске — не забудь обновить `PUBLIC_URL` и перезапустить uvicorn.

### 8. Коммит и PR

```bash
git add <конкретные файлы>
git commit -m "fix: radio artist repetition (#12)"
git push -u origin fix/12-radio-duplicate
```

Открой PR `fix/12-radio-duplicate → main`, укажи `Closes #12`, что
изменено, как проверено, риски. Дождись зелёного CI.

### 9. Merge и проверка прода

Squash merge в `main`, удали ветку. Railway пересоберёт приложение.
Проверь:

- в Deploy Logs есть `Telegram webhook and menu button set for ...`;
- `https://<домен>/healthz` отвечает `{"ok": true}`;
- `/start` в боте открывает Mini App.

Затем обнови локальный `main` и удали worktree:

```bash
git checkout main
git pull
git branch -d fix/12-radio-duplicate
```

### 10. Следующий баг

Новая ветка — снова от свежего `main`. Не продолжай в старом чате и не
тащи в новую ветку другие задачи.

## Definition of Done

- [ ] Issue существует, PR ссылается на него (`Closes #N`).
- [ ] Регрессионный тест падал до фикса и проходит после.
- [ ] `pytest -m "not integration" -v` зелёный локально.
- [ ] CI на PR зелёный.
- [ ] `git diff --stat main...HEAD` содержит только разрешённые файлы.
- [ ] Ручной smoke-тест на тестовом боте пройден.
- [ ] PR просмотрен, выполнен squash merge, ветка удалена.
- [ ] Прод: `/healthz` отвечает, `/start` работает.
- [ ] Worktree/чат закрыт.

## Откат

- **Приложение:** Railway → Deployments → предыдущий успешный деплой →
  Redeploy.
- **Код:** `git revert <merge-sha>` в отдельной ветке и PR.
- **База:** перед фиксами, меняющими схему, сделай копию `/data/lammot.db`
  на volume Railway. `init_db` использует `CREATE TABLE IF NOT EXISTS` и
  не мигрирует существующие таблицы.
- Сначала откат, потом спокойный разбор в новой ветке. Не чинить прод
  руками.

## Частые вопросы

**Почему нельзя мержить без ручной проверки?**
Потому что merge в `main` сразу деплоит на Railway. Автотесты не видят
особенности Telegram WebView, туннеля и реального YouTube.

**Почему отдельный worktree, а не одна папка?**
Каждый чат получает свою ветку, свой индекс и свою папку. Параллельные
ИИ-сессии не делают `stash`/`checkout` и не мешают друг другу.

**Почему тестовый бот?**
У бота один вебхук. Локальный сервер с прод-токеном отберёт вебхук у
Railway, и прод перестанет отвечать.

**Что делать, если «перестало играть»?**
Сначала проверь, не сломалась ли внешняя зависимость: `yt-dlp` и YouTube
меняются часто. Обновление зависимости — отдельная ветка `chore/`, не
смешивай с фиксом логики.

**Почему squash merge?**
Один баг — один коммит в `main`. История читаемая, откат одного бага не
задевает соседние.
